# Bring your own script or extend an example

## Choose your model and download its inputs

- **Icepack:** follow the reviewed Python/JSON walkthrough below.
- **ISSM:** follow the separate [247-second MATLAB own-script walkthrough](issm_own_script.md). Download its {download}`native ISSM own-script input packet <native-issm-own-script-inputs.zip>` and extract it. The three scripts are under `examples/soft_launch/issm/`; the JSON is under `examples/soft_launch/datasets/`. These four scientific files exactly match the successful submitted ISSM run. This packet is separate from the HDF5/MAT full-field download.

The recorded new example had no editable files; examples with existing files require the explicit replacement option described below. ## Steps

1. Keep a local copy of your original example and expected output. Record the scientific software versions and input checksums. Remove credentials and machine-specific absolute paths.
2. In **Advanced**, open **Editor**. Enter a new example name in **name for new / rename / save-as / clone**, then click **New example**. To extend an application example, enter a new name and click **Clone to My Workspace**. Keep the application copy unchanged.
3. Use **Choose script files**, then **Import script files**, to save your UTF-8 source and helper files into that owned example. Enable **Replace existing script files** only when replacing files already present, such as seeded `run.py` or `runme.m`; otherwise existing files are preserved and import reports the conflict. Each imported file must be at most 2 MiB and use one of `.cfg`, `.ini`, `.json`, `.m`, `.md`, `.par`, `.py`, `.sh`, `.toml`, `.txt`, `.yaml` or `.yml`. Notebooks, binary files, folders, path-bearing names and symlinks are not script imports. Confirm the saved filenames, then explicitly select `run.py` or `runme.m` as **Run target**. Importing neither selects that target nor starts a run. You can still select an existing file for manual edits and **Save**, or use **New file** for an absent filename.
4. Upload reusable inputs through Datasets and reference them. Use relative `data/<filename>` paths in the script.
5. Make the script noninteractive: no prompts, GUI windows, internet downloads, or dependencies absent from the tested image. Write output into `outputs/`.
6. For Icepack, retain final Firedrake fields such as `h` and `u` in module globals so the structured exporter can discover them. A script hiding all state inside a function may finish with figures but no structured fields.
7. For ISSM, retain the solved `md` model for the result-export step and write any additional diagnostics explicitly.
8. Run locally in the matching model environment, then run the same saved files on AWS. Compare with [the reproducibility tutorial](comparison.md).
9. Change one parameter, save, and run again. Confirm both the run provenance and result respond to the change.

Do not compare the two models to one another as an equality test: the packet deliberately uses different native discretizations and solves.

A successful submission has a job ID. A successful model run finishes without a solver error. A complete tutorial also has retrievable logs, nonempty results, a readable figure, and a downloaded archive. Record all of these; a green job status alone is insufficient.
